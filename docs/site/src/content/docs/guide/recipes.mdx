Short, end-to-end flows for wiring `ofga` into scripts, CI, and multi-store
setups. Each recipe is self-contained and safe to copy into a shell script or
CI job.

## CI gate for authorization model tests

<CommandDemo slug="model-test" />

Fail the build if a test regresses or an authorization branch ships untested.
See [model testing](../model-testing/) for how coverage is computed.

```bash
# Fail if overall coverage drops below 80%
ofga model test --coverage --coverage-min 80

# Fail if this branch adds a rewrite branch (a new type/arm/condition
# outcome) that no test exercises, compared against main
ofga model test --coverage-diff main
```

Both exit `3` when the gate trips (a failing test, coverage below the
threshold, or an untested branch added since `main`) and `0` otherwise. Any CI
runner that stops on a non-zero exit will catch it.

## Scripting authorization checks

`--plain` emits tab-separated `key<TAB>value` rows. A single `check` prints
`allowed<TAB>true` or `allowed<TAB>false`. The exit code stays `0` either way,
so scripts branch on the printed value, not the exit status (only a real
error, like an unreachable server, exits non-zero).

```bash
if ofga query check user:anne viewer document:roadmap --plain | grep -q 'true$'; then
  echo "anne can view the roadmap"
else
  echo "anne is denied"
fi

# Which documents can anne view?
ofga query list-objects document viewer user:anne --plain | wc -l

# What can anne do with this one document? (every relation on document, tested)
ofga query list-relations user:anne document:roadmap --plain
```

`list-relations` derives its candidate relations from the object's type in the
latest model, so it needs no argument beyond the user and the object. Pass
`--relation` (repeatable) to test only the ones you name. It runs on top of
`batch-check`, so it needs OpenFGA >= 1.8.0.

## Trading consistency for latency

Reads default to `HIGHER_CONSISTENCY`, which bypasses the server's caches so a
check never sees a stale answer right after a write. That costs latency. On
read paths where a slightly stale answer is fine — a dashboard listing, a
warm-up query — `--consistency MINIMIZE_LATENCY` lets the server serve from
cache instead.

```bash
# Correctness matters: the default, no flag needed.
ofga query check user:anne viewer document:roadmap

# Latency matters more than freshness.
ofga query list-objects document viewer user:anne --consistency MINIMIZE_LATENCY
ofga tuples read --object document:roadmap --consistency MINIMIZE_LATENCY
```

The flag is available on `query check`, `query batch-check`, `query expand`,
`query list-objects`, `query list-users`, `query list-relations` and
`tuples read`. `UNSPECIFIED` hands
the choice back to the server's own default.

## Multi-environment profiles

A profile bundles an API URL, store/model ID, and auth. Add one per
environment and switch with `--profile`/`-p` or `OPENFGA_PROFILE` instead of
re-exporting variables. See [configuration](../configuration/) for the full
field list.

```bash
ofga profiles add prod --api-url https://fga.example.com \
  --auth-method client_credentials --client-id "$FGA_CLIENT_ID" \
  --client-secret-stdin --token-url https://issuer.example.com/oauth/token \
  --audience https://api.fga.example.com <<< "$FGA_CLIENT_SECRET"

ofga --profile prod stores list
# equivalent:
OPENFGA_PROFILE=prod ofga stores list
```

## Bulk tuple writes from a file

`tuples write --file` (and `tuples delete --file`) accepts JSON, JSONL, YAML and
CSV, reading from stdin with `-`. The format is inferred from the extension and
can be forced with `--file-format`; stdin has no extension, so it is read as
JSON unless you say otherwise. Writes are sent in server-sized batches and are
**not** transactional across batches. See [scripting](../scripting/) for the
full automation contract.

```bash
cat > tuples.json <<'EOF'
{
  "tuples": [
    { "user": "user:bob", "relation": "member", "object": "organization:org1" },
    { "user": "user:carol", "relation": "member", "object": "organization:org1" }
  ]
}
EOF

ofga tuples write --file tuples.json
```

The same tuples as CSV, using the column names the official `fga` CLI uses.
Columns may appear in any order, only `user_type`, `user_id`, `relation`,
`object_type` and `object_id` are required, and an unknown column is an error:

```bash
cat > tuples.csv <<'EOF'
user_type,user_id,relation,object_type,object_id
user,bob,member,organization,org1
user,carol,member,organization,org1
EOF

ofga tuples write --file tuples.csv
```

A bulk run no longer stops at the first rejected tuple: it keeps going and
reports `wrote X, failed Y of N tuple(s)` on stderr, followed by each failed
tuple and its reason, then exits non-zero. In JSON/YAML output the payload
carries `successful` and `failed` arrays alongside the existing
`written`/`deleted`, `total` and `complete` fields. Automation should check the
exit status and treat the reported count as already committed rather than
retrying the whole file.

`--failed-file` writes just the rejected tuples, in the same format as the
input and with the reasons stripped, so the file can be fixed and re-run
directly. Because a rejected request fails its whole chunk, re-run with
`--max-tuples-per-write 1` when you need per-tuple attribution:

```bash
ofga tuples write --file tuples.csv --failed-file failed.csv
# fix the rows, then:
ofga tuples write --file failed.csv
```

`--max-tuples-per-write` (default 100) and `--max-parallel-requests` (default 1)
tune throughput for large imports. `--on-duplicate ignore` (write) and
`--on-missing ignore` (delete) make an already-existing or already-absent tuple
a no-op instead of an error; both require OpenFGA 1.10 or newer.

## Raw API escape hatch

<CommandDemo slug="api" />

`ofga api` sends an arbitrary request through the active profile's URL and
auth, useful for endpoints the CLI doesn't wrap yet, or for one-off
debugging.

```bash
ofga api GET /stores

ofga api POST /stores/01H.../check \
  '{"tuple_key":{"user":"user:anne","relation":"viewer","object":"document:roadmap"}}'
```

`--plain` preserves the raw response bytes (only adding a missing trailing
newline), which keeps the output pipeable straight into `jq` or another JSON
consumer.

## Exporting tuples for backup or re-import

`tuples read --json` auto-pages and returns every tuple as
`{"key": {"user", "relation", "object"}, "timestamp"}`. `tuples write --file`
accepts that shape directly, so an export feeds straight back in — no `jq`
reshaping required. The `timestamp` field is ignored on import.

```bash
ofga tuples read --json > backup.json

# ...later, against the same or a different store:
ofga tuples write --file backup.json
```
