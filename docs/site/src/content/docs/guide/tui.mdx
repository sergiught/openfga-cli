Run `ofga` with no arguments to launch the interactive TUI on your real profile. It's a keyboard- **and mouse**-driven cockpit for the whole OpenFGA surface. To try it with no server, run `ofga playground` instead (see [The sandbox playground](#the-sandbox-playground)).

The mapping workspace (`ofga mappings`) is a separate TUI with its own guide: [Syncing events into tuples](../mappings/).

Bare `ofga` uses the same resolved profile as CLI commands: `ofga --profile
staging` opens staging without changing the saved default. Profile, store, and
model switches made inside the TUI are reflected immediately in its footer and
subsequent actions.

**Sections** (switch with `tab`, the number keys `1`–`9`, `ctrl+k` for the command palette, or **click a tab**): Profiles · Stores · Model · Tuples · Changes · Tuple Queries · Assertions · API Logs · Tests. Each tab is labeled with its digit (`[1]` Profiles … `[9]` Tests) as a reminder of the shortcut.

**Highlights**

- 🎨 **Model graph**: the authorization model rendered as a colored tree of types, relations, and inherited (tuple-to-userset) paths.
- 🔎 **Query + resolution tree**: run `check`/`list-objects`/`list-users`/`list-relations` and expand *why* a decision was made.
- ✍️ **Inline editing**: add/delete tuples, edit assertions, and edit the model DSL, with **inline validation** as you type.
- 🎯 **Two ways to narrow the tuples**: `/` searches the rows already loaded, while `f` sends a `/read` filter to the server — the way to reach tuples outside the 500 the pane holds at a time.
- 🖱 **Full mouse support**: wheel-scroll the graph and lists, click tabs and list rows, click the footer keycaps as buttons, and click outside a dialog to dismiss it.
- 🎭 **Themes**: `aurora`, `catppuccin`, `charm`, `dracula`, `gruvbox`, `nord`, `tokyonight`, and a `mono` (NO_COLOR-friendly) theme.

**Keys:** press `?` at any time for the full, context-aware keybinding overlay.

> The TUI only launches on an interactive terminal. In a pipe or CI, bare `ofga` prints help instead of hanging.

## The sandbox playground

`ofga playground` opens the same TUI against a built-in OpenFGA server, under a synthetic profile named `playground`. It needs no server and no network, and it never writes anything about itself to `config.toml`.

```bash
ofga playground           # open the sandbox
ofga playground --reset   # start again from fresh samples
```

The server comes preloaded with seven sample stores: `github`, `gdrive`, `slack`, `custom-roles`, `multitenant-rbac`, `temporal-access` and `expenses`. Open one from the Stores tab. The Tests tab shows that store's own tests. They run against the sample's original model and fixtures, so they keep passing after you edit the store.

The samples come from [openfga/sample-stores](https://github.com/openfga/sample-stores) (Apache-2.0). Their license and notice are vendored in `internal/sandbox/samples/`.

**Keeping your changes.** When you quit after changing anything (stores, models, tuples or assertions), the CLI asks `Keep your playground changes? [Y/n]`. Enter means yes. An unrecognised answer asks again, and three in a row count as no. `n`, end of input or `ctrl+c` mean no. Browsing and running checks never trigger the prompt.

Kept changes are saved to `playground.db` and reopened next time:

| OS | Default location |
| --- | --- |
| Linux | `~/.local/share/ofga/playground.db` |
| macOS | `~/Library/Application Support/ofga/playground.db` |
| Windows | `%LOCALAPPDATA%\ofga\playground.db` |

Set `OPENFGA_PLAYGROUND_DB` to use another path.

If another playground session saved since yours started, yours is not saved over it. The CLI prints where your changes were kept instead.

**`--reset`** starts the session from fresh samples. The old save is replaced only if you keep the new session's changes at the prompt.

A saved playground is left exactly as you kept it. Newer samples shipped by a CLI upgrade only appear after `--reset`.

**Real profiles.** Switching to a real profile from inside the playground behaves exactly like bare `ofga`: it becomes the active profile in your config, and writes go to that server.

The server-side tuple filter (`f`) always needs an object carrying a type — a
whole type (`document:`) or one object (`document:roadmap`). A bare type on its
own also needs a user; a relation can't stand in for either. Object ids match
literally, so wildcards (`document:*`) are rejected rather than quietly matching
nothing, as are usersets (`document:1#viewer`) — the object is an object. The
user field takes any `type:id` reference, including a userset (`team:eng#member`)
or a wildcard (`user:*`). Submitting all three fields blank clears the filter and
re-reads the store, and switching store or profile clears it for you — the types
and ids it names belong to the store it was written for.

## Benchmark and optimize the model

The Model tab can run the same analysis as [`ofga model optimize`](../model-optimizer/) without leaving the TUI.

<CommandDemo slug="playground-optimize" />

**Benchmark (`B`).** Times the model on a small data set synthesized from the model itself (seed 1, depth 6). Nothing is read from the store, so it is safe on a production profile. It does 20 runs, and the timings are indicative only.

**Review (`o`).** Lists the safe rewrites as a checklist you can tick with `space`, or tick or clear all at once with `a`.

- A row that depends on a rewrite you rejected is dimmed with "depends on a rejected rewrite", and it is not applied. When that makes M applied rewrites differ from K ticked, the header shows "(M apply)".
- "Worth a look" lists the findings the optimizer cannot rewrite safely; they are read-only, and selecting one shows its cost per user type, where `inf` means the cost grows with your data.
- If the model is blocked, the review shows the reason instead of the checklist, and `w` does nothing.
- `B` in the review benchmarks the selection, and needs at least one applied rewrite.

**Write (`w`).** Opens a dialog with the diff of the applied rewrites. Write stays disabled until the answer check finishes. Any changed answer blocks the write, while unstable answers only add a note. If the weighted graph can't be built, the dialog shows a warning that the rewrites are proven safe by the rules but not double-checked against answers, and Write is allowed right away. If you are viewing an older model version, the dialog warns that writing makes the optimized copy the latest and drops changes made in newer versions. `y` writes, `esc` goes back to the review, and `↑` `↓` / `j` `k` scroll the diff.

The write creates a new model version. Older versions stay selectable with `m`.

## macOS: ⌘K blanks the screen

On macOS, don't reach for **⌘K** to open the command palette — the palette is
`ctrl+k`. ⌘K is a menu shortcut belonging to the terminal itself (Terminal.app
binds it to *Clear to Start*, iTerm2 to *Clear Buffer*), so it never reaches
`ofga`. It simply erases the screen the TUI is drawn on.

The TUI repaints only the cells that change, so once the terminal has wiped the
screen behind its back the display stays blank apart from the occasional
character an animation happens to touch. Press **`ctrl+l`** to redraw and carry
on — nothing is lost, it is only the drawing that got out of sync. Switching
away to another app and back also repaints, in terminals that report focus
events.

If you want ⌘K to reach `ofga` instead, rebind it in your terminal: in iTerm2,
*Settings → Keys*, and in Terminal.app, *Settings → Profiles → Keyboard*.
